## 0. V1.0 修订说明

本版本基于 V8.1 架构方案及评审建议重写，作为正式执行标准。重点修订如下：

1. **身份层次调整**：统一为 `Organization / Project / Business System / Service / Instance`，即组织 / 项目 / 业务系统 / 服务 / 实例。
2. **组织标识替换**：文档中所有 `company` 统一替换为 `cari`。
3. **证书管理统一收敛**：证书发放、续期、轮换、吊销、CRL/OCSP、紧急广播统一由 **证书管理服务（Certificate Management Service）** 负责，业务不直接访问 CA。
4. **mTLS 与 Request Signature 分离**：将 **mTLS（传输层安全）** 与 **应用层 Request Signature（应用安全）** 拆分为两个独立安全层分别描述。
5. **mTLS 验证策略明确**：验证 Root、验证 Project 必须；Business System、Service 可选。
6. **安全等级调整**：默认优先 mTLS；普通内部服务可用 Request Signature；高安全服务叠加 mTLS + Request Signature。新增安全模式发现与协商机制。
7. **多语言集成调整**：改为 **多语言参考实现与示例代码（Sample Code）**，明确 SDK 与 Sample Code 维护主权分离。
8. **算法术语修正**：严格区分签名算法、摘要算法、加密算法、TLS 套件。SM3 是摘要算法，不是签名算法。
9. **工程化增强**：正式化 Canonical Request、黄金测试向量、验证端本地策略、紧急吊销广播、Enrollment 安全、时间与 Nonce 细节。
10. **补充缺失章节**：网关/登录插件、验收标准、迁移与运维要求。

## 1. 建设背景

项目现场常混合外部系统、第三方服务、内部业务模块，网络边界模糊，并非单一可信集群。突出问题包括：

- 外部非法系统可直连内部接口，仅靠 IP、端口、服务名无法确认调用方身份；
- 同一机器上多个服务缺乏密码学身份隔离；
- 固定 Token、Shared Secret 易泄露、难轮换；
- 服务间调用要求高性能、高并发，安全机制不能成为吞吐瓶颈；
- 需覆盖 K8S、Docker、VM、物理机、边缘设备、TPM/HSM；
- 需支持国产密码算法扩展，满足信创要求；
- 多语言实现必须互操作，签名规范必须严格统一。

因此，必须建立统一服务身份与服务间安全通信基础设施。

## 2. 建设目标

1. 每个服务具有唯一服务身份；
2. 每个服务实例具有独立密码学身份；
3. 私钥只存在于服务实例侧；
4. 服务身份由企业 PKI 体系签发；
5. 服务之间可本地身份验证；
6. RPC 请求不依赖中心化实时认证；
7. 支持 K8S 自动 Enrollment；
8. 支持 Docker、VM、裸机部署；
9. 支持边缘设备与 TPM/HSM；
10. 支持证书自动续期、轮换、吊销；
11. 支持服务级授权；
12. 支持应用层 Request Signature 与 mTLS，并分别独立描述；
13. 支持 Ed25519，并扩展 SM2/SM3/SM4；
14. 与统一微服务平台集成，提供多语言参考实现与示例代码；
15. 建立统一审计、监控、告警、容灾体系；
16. 提供协议规范与跨语言黄金测试向量；
17. 支持 SDK 与 Sidecar/Agent 双模式；
18. 支持协议版本协商与平滑演进；
19. 支持验证端本地策略与国密算法强制校验；
20. 支持算法不支持/不匹配时返回特别错误；
21. 支持 Organization / Project / Business System 标识与平台自身 `framework`/`platform` 标识。

## 3. 总体设计原则

### 3.1 密码学信任优先

```text
Root CA
   ↓
Intermediate CA
   ↓
Service Certificate
   ↓
Service Identity
```

身份必须具有密码学可信来源，不依赖 IP、Hostname、Pod Name、Container ID。

### 3.2 私钥永不离开服务实例

服务实例本地生成 PrivateKey/PublicKey，PrivateKey 永不上传，仅提交 CSR。高安全场景私钥存放于 TPM/HSM，应用仅调用 `Sign()`。

### 3.3 控制面与数据面分离

控制面：Service Registration、Enrollment、Certificate Management、Policy、Renewal、Rotation、Revocation、Audit。  
数据面：Request、Authentication、Signature Verification、Authorization。  
数据面不得因每次 RPC 访问控制面而形成性能瓶颈。

### 3.4 默认无中心化请求认证

正常 RPC 使用本地凭证签名与验证，不要求访问 DB/Redis/etcd/CA。仅 Enrollment、Renewal、紧急吊销、策略更新等控制面操作访问中心服务。

### 3.5 协议严谨性与跨语言一致性

所有签名、验签、规范化规则必须形成正式协议规范，并提供跨语言黄金测试向量，确保 Go、Java、C++、Rust、Python 等实现互操作。

### 3.6 高可用与容错

证书续期、吊销、授权策略等关键路径必须具备降级与容错机制，避免单点故障导致服务中断。

### 3.7 性能优先

高并发场景下，认证与签名验证必须在本地内存完成，避免同步远程调用。

### 3.8 可调试与可观测

参考实现必须提供 Debug 模式，可输出实际参与签名的 Canonical String。所有认证、授权、续期、吊销、时间偏差均需指标化、日志化、审计化。

### 3.9 渐进式兼容

协议、算法、Option、授权策略均支持版本化与灰度发布，保证新旧实现平滑共存。

### 3.10 验证端本地策略优先

验证端可本地配置是否启用验证，以及要求哪些签名算法、摘要算法、TLS 套件。本地策略优先于请求声明，但必须审计、告警，并禁止生产环境随意关闭。

## 5. PKI 信任体系

### 5.1 Root CA

- 离线保存；
- 不参与日常证书签发；
- 不部署到业务服务；
- 私钥严格保护，推荐 HSM；
- 仅用于签发 Intermediate CA；
- 恢复流程、审计流程、双人控制制度化。

### 5.2 Intermediate CA

负责服务证书签发、续期、密钥轮换、证书吊销。推荐按环境划分：

```text
Root CA
   ├── Intermediate CA - Production
   ├── Intermediate CA - Development
   └── Intermediate CA - Edge
```

不同安全域使用不同 Intermediate CA。

### 5.3 CA 高可用

Intermediate CA 多副本、负载均衡，支持 HSM 集群或密钥分片。业务服务绝不能访问 CA PrivateKey。

### 5.4 CA 安全与演练

- Root CA 离线机房、双人授权、操作审计；
- Intermediate CA 使用 HSM/专用 CA 服务器；
- 定期执行密钥恢复、灾难恢复、吊销演练；
- 所有签发、吊销、策略变更记录审计日志。

## 6. Service Identity

服务身份采用以下层次：

```text
Organization
  → Project
    → Business System
      → Service
        → Instance
          → Key / Certificate
```

说明：

- **Organization**：企业/租户，如 `cari`。
- **Project**：项目标识，如 `mining-platform`、`platform`。
- **Business System**：项目下的业务系统标识，如 `device-system`、`alarm-system`；平台自身可使用 `framework` 或 `platform`。
- **Service**：隶属于 Business System 下的具体服务。
- **Instance**：服务实例，如 Pod、容器、VM。
- **Key/Certificate**：实例密码学身份。

示例：

```text
Organization: cari
Project: mining-platform
Business System: device-system
Service: device-service
Instance: pod-8c7d9f...
Key: key-20260910-001
```

平台自身示例：

```text
Organization: cari
Project: platform
Business System: framework
Service: identity-service
Instance: pod-xxx
Key: key-20260910-002
```

## 7. SPIFFE Service Identity

推荐采用 SPIFFE 风格 URI：

```text
spiffe://cari/{project}/{business-system}/{service}
```

示例：

```text
spiffe://cari/mining-platform/device-system/device-service
spiffe://cari/mining-platform/alarm-system/alarm-service
spiffe://cari/platform/framework/identity-service
spiffe://cari/platform/gateway/gateway-service
```

高安全场景可区分实例：

```text
spiffe://cari/mining-platform/device-system/device-service/instance/abc123
```

普通微服务推荐 Service 级身份；需严格区分实例时启用 Instance Identity。  
平台自身 Project 可使用 `platform`，Business System 可使用 `framework` 或 `platform`。

## 8. X.509 Service Certificate

服务证书采用 X.509 v3。推荐：

```text
Version: X.509 v3
Public Key: Ed25519
SAN: URI = spiffe://cari/mining-platform/device-system/device-service
Key Usage: digitalSignature
Extended Key Usage: clientAuth, serverAuth
```

证书中可携带算法 OID，服务端根据证书算法选择验证方式。支持双证书并行：Ed25519 + SM2。

## 9. SAN 是服务身份主体

不采用 CN 作为主要身份判断依据，统一使用 Subject Alternative Name：

```text
URI: spiffe://cari/mining-platform/device-system/device-service
```

服务迁移 K8S → Docker → VM → 物理服务器，身份不依赖 IP、Hostname、Pod Name、Container ID。

## 10. Service Enrollment

PKI 证明“证书是否由可信 CA 签发”。Enrollment 证明“运行实体是否有资格申请该 Service Identity”。

流程：

```text
Workload → Enrollment → 证书管理服务 → Policy Validation → Intermediate CA → Service Certificate
```

### 10.1 服务端控制 SAN

客户端提交 CSR 时，**不得信任 CSR 中的 SAN**。证书管理服务必须：

- 根据 Service Policy 决定最终 SAN/SPIFFE ID；
- 校验 CSR 公钥与申请身份绑定；
- 校验 K8S Bound Token / Enrollment Code / TPM 证明；
- 签发证书时由服务端写入 SAN；
- 拒绝包含未授权 SAN 的 CSR。

### 10.2 K8S 自动 Enrollment

K8S 使用 ServiceAccount + Service Policy 完成自动身份注册。Pod 启动时提交：

```text
Pod → ServiceAccount Token (Bound) + ServiceID + InstanceID + CSR → 证书管理服务
```

证书管理服务验证：

- Token Issuer、Audience、Expiration；
- 使用 TokenReview/OIDC 验证 Token；
- Namespace、ServiceAccount、Pod 绑定关系；
- Service Policy 是否允许自动 Enrollment；
- 镜像、环境、Project、Business System 是否匹配。

验证通过后由 Intermediate CA 签发证书，私钥始终在 Pod 内生成。

### 10.3 Docker / VM / 裸机 Enrollment

采用一次性 Enrollment Code：

- 短 TTL，建议 5 分钟；
- 单次使用，原子消费；
- 绑定 Organization / Project / Business System / Service / Environment；
- 可绑定设备指纹或初始 Device Key；
- 分发渠道安全：KMS、Secret Manager、配置中心加密下发；
- 成功后立即失效；
- 支持撤销未使用 Code；
- 失败尝试限流、锁定、告警。

### 10.4 Edge Device Enrollment

边缘设备可采用 Device Credential 或 TPM + Device Key。  
高安全场景推荐 TPM 私钥生成 CSR，私钥不离开 TPM。  
需验证 TPM 证明，如 EK 证书、PCR 值。  
无 TPM 时，Enrollment Code 必须与设备硬件指纹或预置 Device Key 双向绑定；设备指纹仅作为辅助，不作为强身份。

### 10.5 Enrollment 安全要求

- 所有 Enrollment 请求必须 TLS；
- Code/Token 不得写入日志；
- Code 使用后立即销毁；
- 失败尝试限流、锁定、告警；
- 支持审计与追溯。

## 12. 证书管理服务（Certificate Management Service）

证书发放和管理统一由 **证书管理服务** 负责，业务服务不直接访问 CA。证书管理服务封装 Intermediate CA，提供统一 API、策略校验、生命周期管理、审计与监控。

### 12.1 职责

- 证书签发；
- 证书续期；
- 密钥轮换；
- 证书吊销；
- CRL/OCSP Stapling；
- 紧急吊销广播；
- 证书仓库与元数据管理；
- 证书指纹与资产管理；
- 审计与合规；
- 与 Service Center、OPA/Casbin、监控系统集成。

### 12.2 Certificate 生命周期

完整生命周期：Create → Enroll → Issue → Active → Renew → Rotate → Expire / Revoke。

#### 12.2.1 Certificate 有效期

推荐：

- 普通环境：24h；
- 高安全环境：1h~24h；
- 开发环境：7d；
- 边缘设备：根据离线能力适当放宽，但需监控。

#### 12.2.2 Certificate Renewal

证书 TTL 24h，剩余 6h 自动 Renewal。流程：

```text
Service → Generate New Key → Generate CSR → 证书管理服务 → Intermediate CA → New Certificate
```

容错设计：

- 优先使用新旧证书重叠轮换，不依赖过期后继续使用；
- 如必须宽限，验证端需显式配置 `maxGracePeriod`，并审计告警；
- 普通环境宽限期建议不超过 2 小时；高安全环境禁止宽限；
- 证书管理服务不可用时，本地缓存旧证书并重试续期；
- 证书管理服务多副本、负载均衡、健康检查。

#### 12.2.3 Key Rotation

采用证书轮换重叠机制：

```text
Old Key + Old Certificate → New Key + New Certificate → Grace Period → Old Certificate Expire / Revoke
```

保证轮换过程中无瞬间认证中断。

#### 12.2.4 吊销与紧急失效

- 普通服务依赖短 TTL 自然过期；
- 高安全服务启用 CRL/OCSP Stapling；
- 证书缓存有效期取 `min(证书剩余有效期, 5 分钟)`，高安全场景缩短至 30 秒~1 分钟；
- 证书管理服务维护紧急吊销广播通道；
- SDK/Agent 收到吊销事件后立即失效本地 KeyID/证书指纹缓存；
- 吊销事件记录审计，支持追溯。

### 12.3 紧急吊销广播安全模型

- 证书管理服务对 `RevocationEvent` 签名；
- SDK/Agent 验签后处理；
- 事件包含版本号、时间戳、Nonce，防重放；
- 支持确认与重试；
- 本地持久化，离线恢复后全量同步；
- 结构示例：

```json
{
  "version": 1,
  "event_id": "revoke-20260916-001",
  "key_id": "key-20260910-001",
  "cert_fingerprint": "SHA256:...",
  "revoked_at": 1725950000,
  "reason": "key_compromise",
  "signature": "base64(...)"
}
```

## 13. 应用层 Request Signature（独立安全层）

应用层 Request Signature 用于在业务请求层证明调用方身份与请求完整性，独立于 mTLS。默认请求签名算法 Ed25519。

### 13.1 X-Service-Option

采用版本号 + 位掩码：

```http
X-Service-Option: 1
```

低 8 位为能力位：

| 位 | 含义 |
|---|---|
| bit0 | Body 存在（0=无 Body，1=有 Body） |
| bit1 | Body 压缩 |
| bit2 | 加密 |
| bit3 | 批量请求 |
| ... | 预留 |

第一阶段仅定义 bit0。后续扩展通过协议版本控制。

### 13.2 BodyHash

当 `X-Service-Option` body 位为 0，不计算 BodyHash。  
当 body 位为 1：

```text
BODY_HASH = SHA256(Body)
```

支持算法标识：

```http
X-Service-Body-Digest: SHA256:<hex>
X-Service-Body-Digest: SM3:<hex>
```

Body 压缩或加密后，BodyHash 按实际传输 Body 计算，顺序：先压缩/加密，再计算 BodyHash。

### 13.3 Request Header

```http
X-Service-ID: device-service
X-Service-Key-ID: key-20260910-001
X-Service-Time: 1725950000
X-Service-Nonce: 8f3a2c9d...
X-Service-Option: 1
X-Service-Body-Digest: SHA256:xxxx
X-Service-Signature: base64(...)
X-Service-Protocol-Version: 1
```

无 Body 时 `X-Service-Option: 0`，可不发送 Body-Digest。

### 13.4 Canonical Request 规范化

Canonical String 组成：

```text
METHOD
CANONICAL_URI
CANONICAL_QUERY_STRING
TIMESTAMP
NONCE
OPTION
BODY_DIGEST
SIGNED_HEADERS
CANONICAL_HEADERS
```

各部分以 `\n` 连接，末尾不加多余换行。

规则：

1. **METHOD**：大写，如 `GET`、`POST`。
2. **CANONICAL_URI**：
   - 使用原始 Path；
   - 不做 URL 解码；
   - 去除多余斜杠；
   - 非 ASCII 字符先 UTF-8 编码，再按 RFC 3986 百分号编码；
   - 百分号编码大写，如 `%2F`；
   - 空格编码为 `%20`，不使用 `+`。
3. **CANONICAL_QUERY_STRING**：
   - 先对参数名和值做 RFC 3986 编码；
   - 按编码后参数名字典序升序；
   - 同名参数按编码后值字典序升序；
   - 空值参数保留 `key=`；
   - 不使用 `+` 表示空格。
4. **TIMESTAMP**：Unix 秒。
5. **NONCE**：Base64 或 Hex 字符串，推荐 128~256 位随机数。
6. **OPTION**：`X-Service-Option` 原始值。
7. **BODY_DIGEST**：无 Body 时为空字符串；有 Body 时为小写 Hex。
8. **SIGNED_HEADERS**：
   - 必选：`x-service-id`、`x-service-key-id`、`x-service-time`、`x-service-nonce`、`x-service-option`、`x-service-protocol-version`、`host`；
   - 有 Body 时必选：`x-service-body-digest`；
   - 有 `Content-Type` 时必选：`content-type`；
   - 按 Header 名小写字典序排列，以分号连接。
9. **CANONICAL_HEADERS**：
   - 每个 Header 名小写；
   - 值去除首尾空白；
   - 内部连续空白折叠为单空格；
   - 多值 Header 按出现顺序以逗号连接；
   - 每行格式：`header-name:value`；
   - 行间以 `\n` 分隔。

HTTP/2 与 gRPC 映射：

- HTTP/1.1 `Host` 包含端口；
- HTTP/2 `:authority` 映射为 `host`，包含端口；
- gRPC 使用 `:authority` 作为 `host`；
- 参考实现应接管 URL 与 Header 规范化。

Base64：

- 使用标准 Base64；
- 带 `=` 填充；
- 不 URL-safe 化，除非协议版本另行定义。

伪代码：

```go
canonical := strings.Join([]string{
    method,
    canonicalUri,
    canonicalQuery,
    timestamp,
    nonce,
    option,
    bodyDigest,
    signedHeaders,
    canonicalHeaders,
}, "\n")
```

### 13.5 算法矩阵

| 类别 | 算法 | 说明 |
|---|---|---|
| 签名算法 | Ed25519、SM2 | 用于 Request Signature / mTLS |
| 摘要算法 | SHA256、SM3 | 用于 BodyDigest、证书指纹等 |
| 加密算法 | SM4、AES-GCM | 用于可选加密 |
| TLS 套件 | TLS1.3、TLCP_SM2_SM3_SM4 | 传输层安全 |

SM2 默认采用 SM2-with-SM3，签名格式默认 ASN.1 DER。若使用 RAW 格式，需在 KeyProfile 声明。

### 13.6 Timestamp 与时钟同步

默认时间窗口前后 60 秒。  
边缘设备可放宽至 ±5 分钟，但必须：

- 使用 NTP/Chrony 同步时间，建议多源、NTS、防欺骗；
- 暴露系统时间与 NTP 时间偏差指标；
- 偏差过大时拒绝发起请求或告警；
- 记录时钟漂移审计；
- 处理时间回拨。

### 13.7 Nonce 与 Replay Protection

Nonce 推荐 128~256 位随机数。  
所有写操作、支付、控制类接口强制启用 Replay Cache。  
Replay Cache Key 建议：

```text
ServiceID + KeyID + Nonce
```

分布式场景采用滑动窗口 + 本地缓存 + 布隆过滤器。  
布隆过滤器存在假阳性，可能误拒合法请求，需监控。  
TTL 至少覆盖 2 倍时间窗口。  
Redis 故障时分级：高安全 fail-close，普通可降级但审计。

### 13.8 请求签名

```text
Signature = Sign(PrivateKey, CanonicalString)
```

结果 Base64 放入 `X-Service-Signature`。  
SM2 场景使用对应算法套件。

### 13.9 Service Key ID

每个密钥有 KeyID，如 `key-20260910-001`。  
接收方根据 KeyID 找到对应 Certificate、PublicKey、Service Identity。

### 13.10 ServiceID 验证

Header 中 `X-Service-ID` 不能单独作为身份依据。  
服务端必须验证：

```text
X-Service-ID → Certificate SAN → SPIFFE Identity
```

二者必须匹配。

### 13.11 Certificate 验证

接收服务验证证书链：Leaf → Intermediate → Root。  
检查 NotBefore、NotAfter、KeyUsage、ExtendedKeyUsage、SAN、Certificate Status、Service Policy。  
高安全场景检查 CRL/OCSP Stapling。

### 13.12 Certificate Cache

本地缓存 `KeyID → Certificate → PublicKey → Service Identity`。  
使用 LRU 淘汰，设置内存上限。  
缓存有效期取 `min(证书剩余有效期, 5 分钟)`。  
高安全场景缩短至 30 秒~1 分钟。  
命中缓存时跳过证书链验证，只做请求签名验证。  
收到紧急吊销广播时立即删除对应缓存。

### 13.13 Certificate Fingerprint

使用 `SHA256(Certificate)` 作为指纹，用于缓存、审计、日志、资产管理、Key Rotation、紧急吊销。

### 13.14 完整请求验证流程

```text
Request
→ Read Headers
→ Find Certificate by KeyID
→ Validate Certificate
→ Validate ServiceID vs SAN
→ Validate Timestamp
→ Validate Option
→ If Body → Validate BodyHash
→ Build Canonical String
→ Verify Signature
→ Authorization (OPA/Casbin)
→ Business Handler
```

### 13.15 黄金测试向量与跨语言一致性

必须提供黄金测试向量：

```text
Input:
  Method, Path, Query, Headers, Body, Timestamp, Nonce, Option

Expected:
  CanonicalString
  BodyDigest
  Signature
```

覆盖场景：

- 无 Body / 有 Body / 空 Body；
- Query 空值、多值、同名参数；
- URL 编码边界：空格、`+`、`%`、`/`、非 ASCII；
- Header 大小写、多值、空白；
- Host、Content-Type、HTTP/2 `:authority`；
- Ed25519 与 SM2；
- 协议版本 V1。

多语言参考实现必须通过同一套测试向量，CI 强制校验。

### 13.16 Debug 模式与可观测性

参考实现提供 Debug 模式，输出：

- 实际参与签名的 Canonical String；
- BodyDigest；
- SignedHeaders；
- 使用的 KeyID、算法、协议版本；
- 时间偏差；
- 验签失败原因分类。

### 13.17 验证端本地策略与算法不匹配处理

验证端本地策略配置：

```yaml
verification:
  enabled: true
  requiredSignatureAlgorithms: [SM2]
  requiredDigestAlgorithms: [SM3]
  requiredTlsCipherSuites: [TLCP_SM2_SM3_SM4]
  algorithmMode: strict
  maxGracePeriod: 0s
  insecure:
    allowDisabled: false
    allowedEnvironments:
      - dev
      - test
    allowedSources: []
```

规则：

- 生产环境启动时若检测到 `enabled: false` 且 `allowDisabled: false`，拒绝启动；
- `enabled: false` 仅允许 dev/test 或明确白名单来源；
- 若 `allowedSources` 非空，仅这些来源可跳过验证，其他来源仍正常验证；
- `requiredSignatureAlgorithms` 仅包含签名算法，如 Ed25519、SM2；
- `requiredDigestAlgorithms` 仅包含摘要算法，如 SHA256、SM3；
- `algorithmMode: strict`：必须完全匹配，否则拒绝；
- `algorithmMode: prefer`：优先要求算法，不支持时可降级，但记录告警；
- `algorithmMode: fallback`：仅在明确允许的兼容场景下降级。

验证决策流程：

```text
Request
→ Read X-Service-Key-ID
→ Load Certificate by KeyID
→ 启动自检：enabled=false 是否允许？
→ 判断当前来源是否在白名单：
      若 enabled=false 且环境允许且来源在白名单：
          Audit Warn/Error: verification disabled
          Continue to Business Handler
→ 否则执行算法检查：
      If requiredSignatureAlgorithms not empty:
          If Verifier does not support any required algorithm:
              Return ALGORITHM_NOT_SUPPORTED
          Extract provided algorithm from Certificate / KeyProfile
          If provided algorithm not in requiredSignatureAlgorithms:
              Return ALGORITHM_MISMATCH
      If requiredDigestAlgorithms not empty:
          校验 BodyDigest 算法是否匹配
→ 正常验证：
      Validate Certificate
      Validate ServiceID vs SAN
      Validate Timestamp
      Validate Option
      If Body → Validate BodyHash
      Build Canonical String
      Verify Signature
      Authorization
      Business Handler
```

特别错误定义：

| 错误码 | HTTP 状态 | gRPC 状态 | 含义 |
|---|---|---|---|
| ALGORITHM_NOT_SUPPORTED | 426 Upgrade Required | FAILED_PRECONDITION | 验证端不支持本地要求的国密算法实现 |
| ALGORITHM_MISMATCH | 426 Upgrade Required | FAILED_PRECONDITION | `X-Service-Key-ID` 对应算法与本地要求不匹配 |

响应头：

```http
X-Service-Error-Code: ALGORITHM_MISMATCH
X-Service-Required-Algorithms: SM2
X-Service-Required-Digests: SM3
X-Service-Provided-Algorithm: Ed25519
X-Service-Key-ID: key-20260910-001
X-Service-Protocol-Version: 1
```

响应体示例：

```json
{
  "error": "ALGORITHM_MISMATCH",
  "message": "本地要求国密签名算法 SM2，但 X-Service-Key-ID 对应算法为 Ed25519",
  "required": ["SM2"],
  "provided": "Ed25519",
  "key_id": "key-20260910-001"
}
```

审计要求：

- `verification.enabled: false`：记录 WARN/ERROR，包含环境、服务、来源、路径、时间；
- `ALGORITHM_NOT_SUPPORTED`：记录 required、verifier 支持列表、KeyID；
- `ALGORITHM_MISMATCH`：记录 required、provided、KeyID、来源 SPIFFE ID、目标服务。

安全约束：

- `verification.enabled: false` 仅允许 dev/test 或明确白名单；
- 生产环境启动时若检测到 `enabled: false` 且 `allowDisabled: false`，拒绝启动；
- `enabled: false` 必须显式配置，禁止默认关闭；
- L2/L3 服务禁止配置 `enabled: false`；
- `requiredSignatureAlgorithms` 配置国密时，验证端必须实际加载国密实现，否则启动自检失败；
- 算法不匹配错误必须在进入业务逻辑前返回。

## 14. mTLS（传输层安全，独立安全层）

mTLS 用于传输层双向身份认证与链路加密，独立于应用层 Request Signature。服务拥有 X.509 Certificate + PrivateKey，可直接用于 TLS Client Authentication。Service B 验证 Client Certificate 链、SAN，得到 Caller Service Identity。

### 14.1 mTLS 验证策略

根据业务需求，mTLS 验证策略配置如下：

```yaml
mtlsVerification:
  verifyRoot: required            # 必须验证 Root
  verifyProject: required         # 必须验证 Project
  verifyBusinessSystem: optional  # 可选
  verifyService: optional         # 可选
```

SPIFFE ID 结构：

```text
spiffe://cari/{project}/{business-system}/{service}
```

规则：

- **Root 必须验证**：证书链必须追溯到受信 Root CA；
- **Project 必须验证**：从 SPIFFE ID 中提取 Project，必须与预期匹配；
- **Business System 可选**：可配置是否校验 Business System；
- **Service 可选**：可配置是否校验 Service。

### 14.2 mTLS 与 Request Signature 的关系

- mTLS 偏 Transport Security，保护传输层身份与链路；
- Request Signature 偏 Application Security，保护请求内容与业务层身份；
- 两者可独立使用，也可组合；
- 默认优先 mTLS；
- 高安全服务使用 mTLS + Request Signature。

### 14.3 mTLS 性能

TLS 握手主要发生在连接建立阶段。  
gRPC/HTTP2 Keep-Alive 长连接场景，握手成本被大量 RPC 摊薄。  
mTLS 可作为默认生产方案。

### 14.4 SDK 与 Sidecar/Agent 双模式

- SDK 模式：业务进程内嵌参考实现，高性能，适合内部高频调用；
- Sidecar/Agent 模式：本地代理终止 mTLS、注入签名，适合遗留系统或非侵入式改造；
- VM/裸机可通过 iptables/DNAT 将流量重定向到本地 Agent；
- K8S 可结合 Service Mesh，但身份体系仍统一为 X.509/SPIFFE。

信任边界：

- 明确 TLS 终止点；
- 若 Sidecar 终止 mTLS，必须通过本地再签名或可信通道向应用传递客户端身份；
- 禁止应用直接信任外部传入的身份头；
- Sidecar 到应用之间必须有本地信任机制；
- mTLS 证书与 Request Signature 证书可复用同一套，也可分离，但必须统一轮换。

## 15. 安全模式发现与协商

服务如何知道对端支持 mTLS 还是 Request Signature，或两者都支持？

### 15.1 注册元数据

服务在证书管理服务/Service Center 注册时声明支持的安全模式：

```yaml
service: device-service
project: mining-platform
businessSystem: device-system
securityModes:
  - mtls
  - request-signature
preferredMode: mtls
```

### 15.2 服务策略

目标服务策略可强制要求：

```yaml
securityRequirement:
  mode: mtls+request-signature
  mtls:
    verifyRoot: required
    verifyProject: required
    verifyBusinessSystem: optional
    verifyService: optional
  requestSignature:
    required: true
```

### 15.3 协议协商

- TLS ALPN 协商 mTLS 与协议版本；
- HTTP Header `X-Service-Protocol-Version`；
- gRPC Metadata；
- 可选 `X-Service-Security-Mode` 声明期望模式；
- 若目标要求 mTLS，客户端必须建立 mTLS；若仅要求 Request Signature，则签名；若两者都支持，默认 mTLS，必要时叠加签名。

### 15.4 错误码

| 错误码 | HTTP 状态 | gRPC 状态 | 含义 |
|---|---|---|---|
| SECURITY_MODE_UNSUPPORTED | 426 | FAILED_PRECONDITION | 目标服务要求的安全模式不被支持 |
| MTLS_VERIFICATION_FAILED | 401 | UNAUTHENTICATED | mTLS 验证失败 |
| REQUEST_SIGNATURE_FAILED | 401 | UNAUTHENTICATED | 请求签名验证失败 |

## 16. Authentication 与 Authorization 分离

认证回答“你是谁”，授权回答“你可以做什么”。不能仅因证书有效就允许调用所有服务。

采用策略引擎（OPA、Casbin）实现。示例：

```yaml
source: spiffe://cari/mining-platform/device-system/device-service
target: spiffe://cari/mining-platform/alarm-system/alarm-service
methods:
  - CreateAlarm
  - QueryAlarm
```

策略支持版本化、灰度发布、审计日志。  
策略存储于 etcd 或专用策略中心，运行时缓存于本地。  
策略中心故障时默认拒绝，仅对明确白名单/只读接口降级，且必须审计。  
授权决策记录 source、target、action、result、policy version。

## 17. Gateway 与登录插件场景

外部请求：

```text
User → HTTPS + User JWT → API Gateway / 登录插件
```

内部调用：

```text
Gateway → Service Identity → Service A → Service Identity → Service B
```

身份体系明确分离：

- 外部：User JWT；
- 内部：Service Certificate + Request Signature / mTLS。

登录插件类似 APISIX，负责外部 API 和界面调用，应支持：

- 用户登录、JWT 签发与校验；
- 外部身份到内部 Service Identity 的映射；
- 调用内部服务时注入 Service Identity 签名；
- 审计用户、租户、来源 IP、目标服务。

## 18. 三种安全等级

默认优先选择 mTLS。具体支持方式通过第 15 章安全模式发现与协商确定。

### L1：普通内部服务

```text
默认：mTLS
若无法 mTLS：TLS + Request Signature
```

### L2：核心服务

```text
mTLS
```

### L3：高安全服务

```text
mTLS + Request Signature + 严格 Replay Protection + 短生命周期 Certificate + 严格 Authorization + CRL/OCSP Stapling
```

三种模式共享同一套 Service Identity。  
普通内部服务若使用 Request Signature，必须满足本地验证策略与算法要求。

## 19. 国产密码扩展

默认 Ed25519，支持 SM2/SM3/SM4。统一抽象：

```go
type Signer interface { Sign(data []byte) ([]byte, error) }
type Verifier interface { Verify(data, signature []byte) error }
```

业务层不依赖具体算法。算法由 Certificate + Key Profile 确定。  
定义算法套件，证书携带算法 OID。  
支持双证书并行过渡：服务可同时持有 Ed25519 与 SM2 证书，根据对端能力协商算法。  
TLS 层可评估 TLCP/国密 TLS。  
Go 语言注意：标准库不支持 SM2/SM3，可引入 `gmssl`、`tongsuo` CGO 绑定或纯 Go 实现。  
需关注 CGO 性能开销、交叉编译、ARM64 静态链接与目标环境 `.so` 依赖。

## 22. Option 扩展规划

第一阶段：bit0 = Body 存在。  
后续可扩展 bit1 压缩、bit2 加密、bit3 批量请求等。  
通过协议版本控制兼容性，避免位掩码冲突。

## 29. 安全威胁分析

- **伪造 ServiceID**：无对应 PrivateKey，签名验证失败。
- **伪造 Certificate**：无法获得 CA PrivateKey，无法生成 CA 签名证书。
- **修改 Body**：BodyHash 不一致，签名验证失败。
- **重放攻击**：Timestamp 超窗拒绝，高安全接口 Nonce Replay Cache 进一步阻止。
- **私钥泄露**：立即 Revoke Certificate、Disable Renewal、Issue New Certificate、Rotate Key、紧急广播。
- **Enrollment Code 泄露**：短 TTL、单次使用、设备绑定、限流、审计。
- **K8S Token 盗用**：Bound Token、Audience、Namespace、ServiceAccount、Pod 绑定校验。
- **时间攻击**：NTP/Chrony、漂移监控、Nonce 强制。
- **缓存吊销窗口**：短 TTL、紧急广播、高安全场景 CRL/OCSP。
- **本地误关闭验证**：`verification.enabled: false` 必须显式配置、审计、告警，生产环境禁止随意关闭。
- **算法降级攻击**：本地要求国密算法时，必须严格校验 `X-Service-Key-ID` 对应算法，不匹配立即返回 `ALGORITHM_MISMATCH`，不支持实现返回 `ALGORITHM_NOT_SUPPORTED`。
- **mTLS 验证不足**：必须验证 Root 与 Project；Business System、Service 按需可选。

## 30. CA 安全

Root CA PrivateKey 必须离线/HSM。  
Intermediate CA PrivateKey 使用 HSM/专用 CA 服务器。  
业务服务绝不能访问 CA PrivateKey。  
所有 CA 操作双人授权、完整审计、定期演练。

## 31. 性能设计

运行时认证：

```text
Request → Memory Cache → PublicKey → Ed25519 Verify
```

不访问 DB/Redis/etcd/CA。适合高并发、高 RPC 频率、gRPC、HTTP/2。

优化措施：

- 证书/公钥缓存 LRU，内存上限；
- 分片 Map 避免全局锁；
- `sync.Pool` 复用验签上下文；
- 零拷贝 Canonical String 构建；
- 避免重复证书解析；
- 连接复用；
- 分布式 Replay Cache 使用 Redis + 滑动窗口 + 布隆过滤器；
- 压测验证。

建议 SLO：

- Ed25519 验签 P99 < 1ms；
- SM2 验签 P99 单独压测并设定目标；
- 缓存命中率 > 99.9%；
- 续期成功率 > 99.99%；
- 紧急吊销广播到达时间 < 1s~5s；
- 时间偏差告警阈值 < 100ms。

`verification.enabled: false` 仅用于调试，不纳入生产性能模型。

## 34. Go/Kratos 参考实现

- **Credential Manager**：支持文件、K8S Secret、TPM、HSM 存储私钥。
- **Kratos Middleware**：
  - Client Middleware：自动加载证书、构造 Canonical String、签名、注入 Header；
  - Server Middleware：自动验证证书链、请求签名、Timestamp、Nonce、BodyHash，并调用 OPA 授权；
  - Server Middleware 实现本地验证策略：`verification.enabled`、`requiredSignatureAlgorithms`、`requiredDigestAlgorithms`、`algorithmMode`；
  - 算法不匹配时返回 `ALGORITHM_NOT_SUPPORTED` 或 `ALGORITHM_MISMATCH`。
- **证书续期与轮换**：后台 Goroutine 定期检查证书剩余有效期，自动续期并平滑切换。
- **性能优化**：证书缓存使用分片 Map 或 LRU，验签并行化，`sync.Pool` 复用上下文。
- **Debug 模式**：打印 Canonical String、BodyDigest、SignedHeaders、时间偏差。
- **测试向量**：提供 Go 测试用例，并生成跨语言测试向量。
- **ARM64/CGO**：国产密码库注意交叉编译、静态链接、目标环境依赖。

## 37. 最终结论

公司统一微服务平台采用统一体系：

```text
PKI + X.509 + SPIFFE Service Identity + Service Enrollment
+ Certificate Management Service
+ Ed25519 / SM2 Request Signature
+ mTLS（Root/Project 必验，Business System/Service 可选）
+ Authorization + 跨语言测试向量 + 紧急吊销 + 国产密码扩展
+ 验证端本地策略 + 算法不匹配特别错误
```

身份层次：

```text
Organization
  → Project
    → Business System（平台自身可用 framework/platform）
      → Service
        → Instance
          → Key / Certificate
```

SPIFFE 示例：

```text
spiffe://cari/mining-platform/device-system/device-service
spiffe://cari/platform/framework/identity-service
spiffe://cari/platform/gateway/gateway-service
```

安全模式：

```text
默认：mTLS
普通内部服务：mTLS；若无法 mTLS，则 TLS + Request Signature
核心业务：mTLS
高安全业务：mTLS + Request Signature + 严格 Replay + 短证书 + CRL/OCSP
```

最终形成：

```text
企业统一 PKI
→ Certificate Management Service
→ Unified Service Identity
→ X.509 Certificate
→ mTLS / Request Signature
→ Authentication
→ Authorization
→ Business Service
```

的完整安全基础设施。本 V1.0 版本可作为公司统一微服务平台服务身份认证与服务间安全通信的正式执行标准。
